# Stored Cross-Site Scripting (XSS) — DVWA High Security Level

## Objective
Demonstrate and document a successful Stored XSS attack against DVWA's **Stored XSS** module at **High** security level, running in a local Docker-based lab environment.

## Lab Environment
- **Target:** DVWA (`ghcr.io/digininja/dvwa:latest`) running via Docker
- **URL:** `http://localhost:8082`
- **Backend:** MariaDB 10.6 (`dvwa-db` container)
- **DVWA Security Level:** High
- **Testing Method:** Browser DevTools only (no proxy/interception tool used)

### Step 8: Review the Server-Side Filter Logic
Used DVWA's **View Source** button to inspect the actual PHP sanitization logic for the High level. Confirmed the filter primarily targets variations of the `<script>` tag via regex, but does not strip other tags or event-handler attributes.

![Step 8](Evidences/19.png)

### Step 9: Inject Payload #1
Submitted the following payload into the `message` field:

```html

```

![Step 9](Evidences/20.png)

### Step 10: Verify Execution — Payload #1
Payload executed successfully on page load, popping an alert box containing the active session cookie (`PHPSESSID`), confirming the High-level filter was bypassed.

![Step 10](Evidences/21.png)

---

### Step 11: Inject Payload #2
Submitted a second payload to confirm the bypass works with multiple tag/event-handler combinations:

```html

```

![Step 11](Evidences/22.png)

### Step 12: Verify Execution — Payload #2 (Persistence Confirmed)
On page reload, both stored payloads executed in sequence, confirming Stored XSS persistence — the payloads are saved server-side and re-fire for any user who views the page.

![Step 12](Evidences/23.png)

## Findings Summary
- DVWA's High-level Stored XSS filter blocks `<script>` tag variants via regex but does **not** sanitize other HTML tags or event-handler attributes.
- Payloads such as `<img src=x onerror=...>` and `<svg onload=...>` bypass the filter completely.
- The `maxlength` restriction on the `name` field is enforced **client-side only** and can be removed via browser DevTools without needing an intercepting proxy.
- Successful retrieval of `document.cookie` demonstrates real-world session hijacking risk, since `PHPSESSID` was not marked in a way that prevented JavaScript access in this test.
- The vulnerability is persistent — each page reload re-executes stored payloads for any visiting user.

## Remediation Recommendations
- Replace blacklist-style regex filtering with allow-list based HTML sanitization (e.g., a vetted library like DOMPurify server-side equivalents).
- Enforce input length limits **server-side**, not just via HTML attributes.
- Apply context-aware output encoding when rendering stored user input.
- Set a strict Content-Security-Policy (CSP) to block inline event handlers (`onerror`, `onload`, etc.) even if HTML filtering is bypassed.
- Ensure session cookies are flagged `HttpOnly` (already observed in this environment) to reduce impact even if XSS occurs.
