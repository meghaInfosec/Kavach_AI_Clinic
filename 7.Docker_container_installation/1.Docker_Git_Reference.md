# Docker, Containers, and GitHub Workflow — Reference Guide

## Overview

This document covers two independent workflows:

1. **Docker and container management** — starting Docker and the vulnerable-app containers in the Kali VM lab environment
2. **GitHub setup and push workflow on Windows** — installing Git and pushing documentation/evidence to the KAVACH repository

---

## Part 1 — Docker and Container Management (Kali Linux VM)

### Environment

| Component | Detail |
|---|---|
| Host | VirtualBox VM, Kali Linux |
| User | `kali` (non-root, standard operation) |
| Containers configured | DVWA (port 8082), Juice Shop (port 3000) |
| Related VM | Metasploitable2 (separate, not a Docker container) |

### 1.1 Start Docker

```bash
sudo systemctl start docker
```

### 1.2 Verify Docker is running

```bash
sudo systemctl status docker
```

### 1.3 List all containers (running and stopped)

```bash
docker ps -a
```

This shows container names, image, status, and port mappings. Both `dvwa` and `juice-shop` should appear here once created.

### 1.4 Start a specific container

```bash
docker start dvwa
docker start juice-shop
```

If DVWA depends on a separate database container (e.g. `dvwa-db`, using MariaDB), start that first:

```bash
docker start dvwa-db
docker start dvwa
```

### 1.5 Stop a specific container

```bash
docker stop dvwa
docker stop juice-shop
```

### 1.6 Confirm running containers

```bash
docker ps
```

Only currently running containers appear here (unlike `docker ps -a`, which shows stopped ones too).

### 1.7 Access the applications

| Application | URL |
|---|---|
| DVWA | `http://localhost:8082` |
| Juice Shop | `http://localhost:3000` |

### Troubleshooting note — DVWA database connection error

If DVWA shows a `mysqli_sql_exception: getaddrinfo for db failed` error, the database container (`dvwa-db`) is stopped or not on the same Docker network. Fix:

```bash
docker start dvwa-db
docker ps | grep dvwa-db
```

Then reload the DVWA page.

## Part 2 — Installing Git on Windows

### 2.1 Download the installer

Go to: `https://git-scm.com/download/win`
Download the 64-bit Windows installer and run it.

### 2.2 Installer options (recommended defaults)

Step through the installer accepting defaults, with these two exceptions:

| Screen | Recommended selection |
|---|---|
| Choosing the default editor | **Use Notepad as Git's default editor** (simpler than the default Vim for beginners) |
| Adjusting your PATH environment | **Git from the command line and also from 3rd-party software** (already the recommended default — enables `git` in both CMD and PowerShell) |

All other screens (branch naming, HTTPS backend, line endings, terminal emulator, `git pull` behavior, extra options) can be left on their defaults.

### 2.3 Verify installation

**Close any open Command Prompt windows** and open a fresh one (required for PATH changes to take effect), then run:

```cmd
git --version
```

Expected output resembles:
```
git version 2.55.0.windows.1
```

## Part 3 — Cloning the Repository

### 3.1 Navigate to the desired parent folder

```cmd
cd C:\Users\<YourUsername>\Desktop
```

### 3.2 Clone the repository

```cmd
git clone https://github.com/meghaInfosec/Kavach_AI_Clinic.git
```

This creates a `Kavach_AI_Clinic` folder containing a proper `.git` directory — required for `add`/`commit`/`push` to work. (A ZIP download from GitHub's "Download ZIP" button does **not** include this and will not function as a Git repository.)

### 3.3 Navigate into the project

```cmd
cd Kavach_AI_Clinic
```

## Part 4 — Adding Files and Pushing to GitHub

### 4.1 Check current status

```cmd
git status
```

Shows untracked files, staged changes, and whether the local branch is ahead of `origin/main`.

### 4.2 Stage changes

To stage everything:
```cmd
git add .
```

To stage a specific folder or file only:
```cmd
git add "path\to\folder"
```

### 4.3 Commit staged changes

```cmd
git commit -m "Descriptive commit message here"
```

Use a message that clearly states what changed, e.g. `"Add Medium level Stored XSS writeup with evidence"`.

### 4.4 Push to GitHub

```cmd
git push
```

### 4.5 First-time authentication

On the first push from a new machine, a **"Connect to GitHub"** dialog appears:

1. Select **"Sign in with your browser"**
2. Log into the GitHub account in the browser window that opens
3. Click **"Authorize git-ecosystem"** on the permissions screen
4. Wait for the redirect to complete (do not close the tab immediately — allow 10–15 seconds)
5. Return to the terminal — the push completes automatically once authorization is confirmed

Subsequent pushes from the same machine do not require re-authentication unless credentials are cleared or a different account is used.

### 4.6 Pulling remote changes before pushing (if needed)

If the remote repository has changes not present locally (e.g. edits made directly via GitHub's web interface), pull before pushing:

```cmd
git pull
```

Resolve any merge prompts, then proceed with `git add`, `git commit`, and `git push` as above.
